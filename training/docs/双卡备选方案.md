# LoRA 双卡 DDP 备选（Windows 原生）

这是额外的 LoRA 双卡方案，使用 PyTorch `DistributedDataParallel` 和 Gloo，一卡一个进程。原有 `train.py`、`train_lora.py`、`configs/train.yaml`、`configs/lora.yaml` 及其 PowerShell 入口均保持原样。MLP也已有独立双卡训练入口，详见 `MLP双卡备选方案.md`。

## 使用

进入工程目录后，先验证目标两张A4000：

```powershell
# 快速验证：两进程、两张不同GPU、Gloo CUDA all-reduce及DDP梯度平均。
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check_ddp.ps1 -EnvDir D:\SCC_Retrieval_A\env -Output artifacts\ddp_check_01
# 完整合成小测：实际DINO、两轮DDP训练、全候选验证、导出及重载。
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check_ddp.ps1 -EnvDir D:\SCC_Retrieval_A\env -FullSmoke -Output artifacts\ddp_smoke_01
# 正式训练沿用已准备并核验的原manifest，输出到独立目录。
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\train_lora_ddp.ps1 -EnvDir D:\SCC_Retrieval_A\env -Manifest artifacts\real\manifest.json -Run artifacts\real\lora_ddp
```

默认设备 `cuda:0,cuda:1`，可用 `-Devices` 指定两张可见GPU。生产入口要求两个不同CUDA设备，缺第二张卡就明确报错，不会静默退回单卡。换用原单卡入口即可继续原方案：`scripts/train_lora.ps1`，其默认输出仍为 `artifacts/real/lora`。

分布式入口直接使用 `torch.multiprocessing.spawn` 和 FileStore 启动标准DDP，不必外套 `torchrun`，也无需依赖某个Windows wheel是否编译了libuv TCPStore。Gloo仍使用本机进程间通信；离线运行不需要互联网，不能用阻止所有本地socket的旧单卡网络保护器包住DDP。不会自动修改防火墙、网络设置或驱动。通信失败请查看预检日志。

## 批量、损失与采样

独立配置为 `configs/lora_ddp.yaml`。默认 `global_batch_groups: 4` 是两张卡合计每次更新4个查询组，每卡通常累积2组，与原单卡每4组更新的有效批量相同。学习率保持1e-4，不能把单卡的累积4组机械地复制为每卡4组而仍声称批量不变。每组候选采样、GeM和损失定义沿用原实现。

每个查询及其候选属于同一个worker；一组内的多次图像微批前向封装在一次DDP前向中。只同步LoRA参数梯度，各worker独立严格校验并加载同一冻结DINO，避免广播全部冻结权重。没有跨组增加负样本。

全局训练顺序由相同种子和epoch生成，然后分配到各rank；原分组平衡产生的过采样保留。最后一批不足时，用零损失占位保持各rank反向次数相同，不补入重复训练样本，按真实组数加权。验证按查询分片，不补样本，严格校验最终查询ID集合；无正候选仍计入总体召回失败。困难负例只在训练集分片挖掘并汇总。

## 恢复、评估和输出

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\train_lora_ddp.ps1 -EnvDir D:\SCC_Retrieval_A\env -Run artifacts\real\lora_ddp -Resume artifacts\real\lora_ddp\last.pth
# 验证/最终测试可直接复用现有评估入口；这里是单卡全候选比较，不改变DDP训练。
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\evaluate_lora.ps1 -EnvDir D:\SCC_Retrieval_A\env -Run artifacts\real\lora_ddp -Split val
```

新训练要求空目录；恢复使用原目录并保留best。只由rank0写best/last/history和汇总报告，checkpoint包含各rank随机数状态、优化器、AMP scaler、困难负例及统一早停状态。数据、配置、代码、world size、设备选择或PyTorch版本变化会拒绝恢复；单卡checkpoint不能作为DDP断点恢复。导出的adapter结构和加载方式与原单卡LoRA一致。

- `job_status.json`：最近一次启动的权威状态，running/paused/complete/failed。
- `rank_0.log` / `rank_1.log`：各进程日志，恢复时追加；失败另有 `rank_*_failure.json`，可能保留历史失败，判断当前状态以job_status为准。
- `rank_*_status.json`：当前阶段及处理的查询ID。`rank_*_epoch_*.json`：已处理ID及参数指纹。
- `history.json/csv/png`：训练损失、验证R@1、更新数、AMP溢出跳步和副本参数哈希。
- `performance_epoch_*.json`：每个worker训练用时、查询数、CUDA allocated峰值和总体吞吐。训练计时包含通信及状态日志I/O，不包含困难负例挖掘/验证。
- `best_validation_review.json` 与对应reports目录：最佳验证的HTML、CSV、候选图。测试集只在固定方案后最终评估。

单rank失败会使整次作业失败，并由父进程结束其他worker；不会把半份数据结果当成完整评估。OOM时减小单组正负例数量或图像微批量，保留梯度检查点；DDP不会把两张16GB卡自动合成一块32GB显存。

## 已验证范围

准备机只有一张RTX4060。已在PyTorch2.5.1+cu118下实测两进程Gloo的CPU/CUDA all-reduce和DDP梯度平均。两进程CPU测试覆盖梯度累积与不齐尾批相对串行均值的等价性、查询分片、未覆盖召回、失败联动，以及有dropout的中断恢复：连续运行与恢复后的历史和适配器张量一致。

另外用真实本地ViT-L/14在同一张4060上启动两个进程，完成12合成查询/300候选中的训练和全量验证、两轮DDP训练、导出重载；两份适配器参数逐轮一致，A/B均获得梯度，冻结基座无梯度，导出重载最大误差为0。loss为1.090235、1.087155，仅验证管线，不代表真实精度。

同卡测试明确记录 `diagnostic_only=true`、`distinct_gpu_test_passed=false`，不等同于两张A4000验收，也不能用于报告双卡加速比。目标服务器须运行上面的快速预检和完整小测，两个独立GPU通过后才会记录 `distinct_gpu_test_passed=true`。

参考：[PyTorch 2.5.1通信后端说明](https://github.com/pytorch/pytorch/blob/v2.5.1/docs/source/distributed.rst)、[对应版本DDP实现与文档](https://github.com/pytorch/pytorch/blob/v2.5.1/torch/nn/parallel/distributed.py)。原生Windows不依赖NCCL，本包使用已实测可用的Gloo路径；目标硬件性能需要实际测量。
