# 训练 / 推理更新与运行指南（2026-11-06，仅垂直视角 DV/NV）

本次更新只在 Linux CPU 上用合成数据和单元测试验证过（训练端 110 项通过（含合成数据上 prepare → 提特征 → 训练 → 导出 → 推理端加载的端到端测试），推理端 40 项通过；另有 2 项 C++ 编译相关的测试失败，原来就存在，与本次改动无关）。**还没有在真实数据、Windows 训练服务器的 GPU 或 Orin 上运行过。**按下面的顺序先跑小样本，确认通过后再跑全量。

## 一、改了什么

### 训练端（`training/`）
| 内容 | 说明 |
|---|---|
| 候选块按推理原代码生成 | `scc_geodata.py` 是推理 `geodata.py` 的逐字节拷贝；`scc_inference.py` 逐字拷贝了 `camera_matrix`、`optical_pose`、`dumpRotateImage`、`estimate_reference_side`、`compute_block_mid_wo_black`、`crop_center`。地图网格、旋转、块尺寸、50% 步长、黑边过滤都与推理一致，查询图预处理逐像素一致 |
| 搜索窗 | 中心 = 真值 + ≤300 m 随机偏移，高度 = 真值 ± 100 m。两种方案（`candidates.window_mode`，与推理一致）：`meters` 固定边长（训练、验证默认均为 4000 m）；`blocks` 固定每帧块数（窗口随 AGL 变化）。窗口至少能放下旋转后的块，且不小于 2 个块宽 |
| 样本数量 | 训练集每个查询保留全部正样本 + 128 个负样本（一半最近、一半随机），首轮每 3 帧取 1 帧（`train_query_stride`）；验证/测试保留全部块，每 5 帧取 1 帧 |
| GPU | 只用显存 ≥ 6 GB 的卡（两张 A4000）。一键脚本自动选择并打印 `Using GPU cuda:i = ...`；指定到显存不足的卡（如 P400）时直接报错 |
| 标签 | 覆盖率 ≥ 0.6 为正样本，≤ 0.05 为负样本，中间的忽略 |
| 卫星强度检查 | inspect / prepare / 候选图会统计映射后纯白、纯黑像素的比例，超过 90% 时报错并给出建议的 `image_value_range` |
| 配置 | 精简配置 `configs/mlp.yaml`（`base: train.yaml`），只含 DV/NV 两组，`nadir_reference_alignment: true` |
| 一键脚本 | `scripts/run_mlp.ps1`：prepare → 候选图 → 双卡提特征 → 训练并导出 → 验证集评估 |
| 删除 | 旧的多尺寸候选协议、增量更新打包/安装脚本（运行 `apply_update.ps1` 删除） |

### 推理端（`inference/`）
| 内容 | 文件 |
|---|---|
| 加载训练好的 MLP 检索头（以前**完全没有加载**） | `single-so/python/retrieval_head.py`，`projects/SCC-Loc/Retrieval_Models/feature_extract.py`，`backends.py` |
| 先验跟踪：定位经下一帧确认后，以"上次定位 + 速度"为中心用小窗口跟踪；捕获阶段在平滑先验周围逐帧扫描 | `single-so/python/prior_tracker.py`，`backends.py`，`worker.py` |

| 窗口下限：至少能放下旋转后的块（避免 REF_WINDOW 报错） | `backends.BaseBackend.window_for_block` |

## 二、训练端

### 2.1 更新代码（离线服务器，只需拷贝一次）
有两种方式，任选一种：
- **覆盖更新**：把 `vis-loc_training_update_20261106.zip` 解压覆盖到现有工程目录（例如 `D:\SCC_Retrieval\project`），然后运行：
  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File D:\SCC_Retrieval\project\apply_update.ps1
  ```
- **全新目录**：把 `vis-loc_training_full_20261106.zip`（完整的训练源码）解压到一个新目录，环境仍用原来的 `D:\SCC_Retrieval\env`，DINO 源码目录 `vendor/dinov2` 从旧工程拷过来。

旧的 manifest 和特征缓存都已失效（源码指纹变了），需要用新的 `output` 目录。

### 2.2 填写 `configs/mlp.yaml`
| 字段 | 填什么 |
|---|---|
| `data.root`、`geo.satellite`、`geo.dsm` | 实际路径 |
| `split.sequence_splits` | 实际出现的全部序列名 → train / val / test |

### 2.3 调试（小样本，必须先跑）
```powershell
cd D:\SCC_Retrieval\project
$py = 'D:\SCC_Retrieval\env\python.exe'
& $py inspect_dataset.py --config configs/mlp.yaml
powershell -ExecutionPolicy Bypass -File scripts\run_mlp.ps1 -EnvDir D:\SCC_Retrieval\env -Limit 12 -Steps prepare
```
检查以下几项：
1. `artifacts/mlp/inspection.json`：`errors` 为空；`rasters.satellite_intensity` 中 `mapped_white_fraction` 和 `mapped_black_fraction` 都应接近 0（白的多说明 `image_value_range` 上限太低，黑的多说明下限太高）。
2. `artifacts/mlp/preparation_report.json`：
   - `failures`：如果出现 `non-EO nadir alignment requires near-zero ...`，说明有帧的 sensor 角或 INS pitch/roll 超过了 1°。这类帧多的话需要放宽门限，推理端和训练端要一起改。
   - `covered_queries` 应接近 `split_counts`，即几乎每帧都有正样本。
   - `block_side_m` 约为 0.37 × AGL；`candidates_per_split` 用来估算提特征的耗时。
3. `artifacts/mlp/diagnostics_prepare_*/contact_sheet.png`：概览图是推理实际看到的旋转后搜索地图。绿色的真值足迹应该落在黄框（展示的块）附近；候选块不应是纯白或纯黑。

### 2.4 训练
服务器有 3 张卡（A4000 × 2 + P400），只用两张 A4000：提特征时双卡并行，MLP 训练和评估用其中一张。一键脚本会自动选卡并打印 `Using GPU cuda:i = NVIDIA RTX A4000 (16.0 GB)`。如果打印出来的不是两张 A4000，用 `-DeviceIds 0,1` 手动指定（编号以脚本打印的为准）。

**首轮快速出结果**：`mlp.yaml` 默认已按快速设置：
- 训练集每 3 帧取 1 帧（`train_query_stride: 3`），验证/测试每 5 帧取 1 帧；
- 训练窗口 2000 m；
- 提特征 batch 32。

提特征量 ≈ 训练帧数 / 3 × 约 130 + 验证测试帧数 / 5 × 每帧块数。比如 4000 个训练帧约 17 万张图块，双卡大约 20–30 分钟（按每秒 100–150 张估算，以日志实测为准）。MLP 训练在缓存特征上进行，单卡每轮很快。首轮结果正常后，把 `train_query_stride` 改为 1，换一个新的 `output` 再跑全量。

```powershell
# 全流程：prepare → 双卡提特征 → 训练并导出 → 验证集评估
powershell -ExecutionPolicy Bypass -File scripts\run_mlp.ps1 -EnvDir D:\SCC_Retrieval\env
# 只重跑某几步（例如 prepare 已完成）
powershell -ExecutionPolicy Bypass -File scripts\run_mlp.ps1 -EnvDir D:\SCC_Retrieval\env -Steps extract,train,eval
# 手动指定 GPU（编号以 'Using GPU' 打印为准），或只用一张卡
powershell -ExecutionPolicy Bypass -File scripts\run_mlp.ps1 -EnvDir D:\SCC_Retrieval\env -DeviceIds 0,1
powershell -ExecutionPolicy Bypass -File scripts\run_mlp.ps1 -EnvDir D:\SCC_Retrieval\env -GPUs 1 -Steps extract
# 双卡 DDP 训练（可选，MLP 单卡已经够快；自动选两张 ≥6 GB 的卡）
powershell -ExecutionPolicy Bypass -File scripts\train_mlp_ddp.ps1 -EnvDir D:\SCC_Retrieval\env -DataRun artifacts/mlp
# 选定模型后，用测试集做最终评估
& $py evaluate.py --manifest artifacts/mlp/manifest.json --cache artifacts/mlp/features --checkpoint artifacts/mlp/training/best.pth --split test --output artifacts/mlp/evaluation_test.json --device cuda:0
```
- 训练输出：`artifacts/mlp/training/`（`best.pth`、`history.png`）；导出：**`artifacts/mlp/scc_retrieval_head.pth` 及同名 `.json`**（部署用）。
- 判断训练是否有效：评估报告（`evaluation_val_reports/*/index.html`）中，`heads` 的 R@1 应明显高于 `gem1024`（原始检索）。如果没有提升，推理端先不要配置 `retrieval_head`。
- 嫌慢可调：`candidates.train_negatives`（128 → 64）、`eval_query_stride`（5 → 10）。提特征中断后，重跑同一命令会自动跳过已完成的部分。
- 训练输出目录必须为空。重跑训练前换一个 `output`，或者删除 `artifacts/mlp/training`。

## 三、推理端

### 3.1 源码
`vis-loc_inference_full_20261106.zip` 是完整的推理源码（`single-so/` 的 C++、Python 适配层、工具和测试，以及 `projects/SCC-Loc`、`projects/AnyVisLoc-Benchmark` 两个算法目录），不含 ARM64 运行环境、权重和地图。
`vis-loc_inference_update_20261106.zip` 只含本次改动的文件，可以覆盖到已有的源码树上。

### 3.2 编译 .so（ARM64 Ubuntu，与比赛机一致）
编译需要 cmake、g++、python3。除了源码，还需要 `runtime.tar.gz`，即内嵌的 Python 环境、依赖库和原生库。最简单的办法是从现在能用的旧 .so 里直接取回，**一条命令完成**：
```bash
cd inference/single-so
bash rebuild_from_old_so.sh /path/to/old/libvNavigatorInterface.so
# 输出 dist/libvNavigatorInterface.so 和 dist/SHA256SUMS，最后打印 RUNTIME_OK 表示内嵌运行时自检通过
```
这个脚本依次执行以下步骤，也可以手动逐步运行：
```bash
python3 tools/extract_runtime.py /path/to/old/libvNavigatorInterface.so runtime.tar.gz   # 1. 从旧 .so 取回运行时（校验 SHA256）
rm -rf runtime-stage                                                                     # 2. 删掉旧的展开目录
python3 tools/repack_runtime.py                                                          # 3. 用新的 python/ 和 projects/ 更新运行时
bash build.sh                                                                            # 4. cmake 编译 + 附加运行时 → dist/
build/runtime_check dist/libvNavigatorInterface.so && echo RUNTIME_OK                    # 5. 自检
```
- 如果没有可用的旧 .so，只能在准备好的板子上用 `tools/capture_runtime.py --source-home <home>` 重新捕获运行时（需要 `~/.venvs/uavloc` 和 `wheelhouse/`），然后运行 `bash build.sh`。
- 最终的 .so 不能 strip 或 objcopy，否则会丢掉附在末尾的运行时。
- **保留旧 .so 作为回退。**

### 3.3 配置 naviParams.txt（`infrared` 段，参考 `naviParams.example.txt`）
```yaml
infrared:
  pose_priori: yp
  retrieval_head: ./weights/scc_retrieval_head.pth   # 训练导出的头（相对 naviParams 所在目录）；删掉这一行 = 原 GeM 检索
  reference: {...}                                   # 与训练 mlp.yaml 的 inference.reference 一致
  camera:
    reference_window_scale: 1.2
    nadir_reference_alignment: true                  # 垂直视角必须为 true
  prior_tracking: {enabled: true, acquisition: scan, prior_error_m: 5600, altitude_error_m: 200,
                   window_mode: meters, max_window_m: 4000, max_blocks: 100, hard_cap_m: 8000,
                   min_window_m: 600, min_fix_inliers: 40}
```
把 `scc_retrieval_head.pth`（及 `.json`）拷到 `weights/`，和 DINO、RoMa 等权重放在一起。

### 3.4 上机检查与调参
运行后查看日志：
| 日志 | 看什么 |
|---|---|
| `[RETRIEVAL_HEAD] loaded ... (512-d)` | MLP 头已加载。没有这一行，说明仍在用原 GeM 检索 |
| `[PRIOR_TRACK] mode=scan/tentative/track window=...` | 状态与窗口。正常情况下应在几十帧内进入 `track` 并保持 |
| `[PRIOR_OUT] source=fix/predicted/...` | 每帧输出的来源。如果在 `track` 状态下长期是 `predicted`，说明可能跟错了 |
| `[NAV_TIMING] ... total_s` | 单帧耗时，要在 10 秒以内。两种方案任选：**`meters`**：先试 `max_window_m: 4000`，超时就降到 3000（模拟得分 2000/3000/4000 m 约 0.5/0.7/0.8）；**`blocks`**：调 `max_blocks`，每帧块数基本固定，耗时也就稳定（窗口随 AGL 变化，日志里的 `cap` 和 `block` 就是本帧的窗口上限和块边长）。训练端 `window_mode`、`eval_window_m` / `eval_max_blocks` 同步修改 |

### 3.5 回退
| 问题 | 回退方法 |
|---|---|
| MLP 头效果不好 | 删除 `retrieval_head` 这一行 |
| 跟踪不稳定 | `prior_tracking: {enabled: false}`（恢复为以先验为中心的固定 `window_m` 窗口） |
| 新 .so 有问题 | 换回旧 .so |

## 四、已知限制
- 非 EO 帧在 `nadir_reference_alignment` 下要求 sensor 角和 INS pitch/roll 都在 1° 以内（推理原代码），超出的帧会失败。
- 推理端的 isEO 来自初始化参数，训练端按每帧记录。
- 推理端 DINO 用 fp16 权重，训练端用 fp32 + autocast，数值差异很小。
- 跟踪和捕获的效果数字来自模拟；真实的误锁率、检索成功率和每帧耗时都需要在目标机上实测。
